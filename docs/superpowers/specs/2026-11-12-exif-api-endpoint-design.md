# Metaforge EXIF API endpoint + n8n Worker integration

Date: 2026-11-12
Status: approved by owner 2026-11-12

## Intent

Images generated by the n8n pipeline "Fal.ai Image Generator" currently land in
Google Drive carrying whatever metadata Fal.ai / OpenAI emit, and none of ours.
The owner wants every generated image stripped of all metadata and stamped with
three fields before it reaches Drive: **Author**, **GPS Latitude**, **GPS
Longitude**, with the values coming from the spreadsheet row that produced the
image.

Metaforge (this repo, deployed at https://meta-forge-ten.vercel.app) already
contains tested strip-and-stamp code for JPEG, PNG and WebP, but only as a
browser UI. This project exposes that code as an HTTP endpoint and wires the
n8n Worker to call it. One implementation of the EXIF logic, used by both the
UI and the pipeline.

## Goals

1. A new HTTP endpoint on the Metaforge Vercel deployment that accepts one
   image plus author / latitude / longitude, strips all metadata, writes those
   fields, and returns the processed image.
2. The n8n workflow **Fal.ai Image Generator - Worker** (id `QHneqwqMa6AlUA5P`)
   calls that endpoint between its "Download Image" and "Upload to Drive"
   nodes, so the file uploaded to Drive is the stamped one.
3. The endpoint is not usable by anyone who does not hold a shared secret.
4. The existing browser UI keeps working exactly as before.

## Non-goals

- No change to the dispatcher workflow **Fal.ai Image Generator**
  (id `9OrGyT0Mnwb2wxbx`).
- No other metadata fields via the API (the UI's full field set is not exposed).
- No TIFF support (same as the UI today).
- No change to how the Worker names files, which Drive folder it uses, or how
  it updates the sheet.
- No UI for the API (no docs page, no key management screen).

## Anti-goals (what would make this a failure even if it "works")

- Two divergent copies of the EXIF logic. The endpoint must import the
  existing `src/lib/exif` code, not re-implement it.
- An open endpoint on the public internet that anyone can POST images to.
- Silently uploading an un-stamped image to Drive when the stamping step fails.
  A failure must fail the row.
- Breaking the Vite static build or the current UI deployment.

## Constraints

- **Hosting:** Vercel, auto-deploys from the `main` branch of
  `github.com/admin-pracxcel/meta-forge`. Serverless function request bodies
  are capped at 4.5 MB. GPT Image 2 output at 768x960 is ~1-2 MB PNG, so this
  is fine today; the design should return a clear error (not a crash) if a
  larger image ever arrives.
- **Runtime:** Vercel Node.js functions. The existing `src/lib/exif` code uses
  only `Uint8Array`, `TextEncoder` and `piexifjs`, all of which run under Node
  (the repo's `scripts/smoke.mjs` already proves this).
- **n8n:** self-hosted at https://n8n.pracxcel.com.au, edited through the
  n8n public API via MCP. The Worker's nodes: executeWorkflowTrigger →
  Fal.ai → HTTP Request (download, binary out in property `data`) → Google
  Drive upload → Google Sheets update. Google credentials are
  `admin@conquerradigital.com`.
- **Spreadsheet:** the owner will add three columns to Sheet1 of the
  "Fal.ai Image Generator" sheet, named exactly `Author`, `Latitude`,
  `Longitude`. Latitude / Longitude are decimal degrees, negative for
  South / West (same convention as the Metaforge UI).
- **Local repo state:** the working folder is not a git repo and `gh` is not
  installed. `git` and SSH keys are present. Deploying means getting the commit
  onto `main` on GitHub.

## Design

### 1. Metaforge API endpoint

**Route:** `POST https://meta-forge-ten.vercel.app/api/process`
Implemented as a Vercel serverless function at `api/process.ts` in the repo
root, importing `stripAndApply` / `detectFormat` / `mimeFor` from
`src/lib/exif`.

**Authentication:** header `Authorization: Bearer <key>`. The key is compared
against the Vercel environment variable `METAFORGE_API_KEY`. Missing or wrong
key → `401` JSON. If the env var is not set at all, the endpoint refuses every
request with `503` JSON ("API key not configured") rather than running open.

**Request body:** `multipart/form-data` with fields:

| field       | type   | required | notes                                     |
| ----------- | ------ | -------- | ----------------------------------------- |
| `file`      | file   | yes      | JPEG, PNG or WebP                         |
| `author`    | text   | no       | blank / missing → not written             |
| `latitude`  | text   | no       | decimal degrees, -90..90                  |
| `longitude` | text   | no       | decimal degrees, -180..180                |

Semantics follow the UI: the file is **always fully stripped**; each field is
written only if present and non-blank. GPS is written only if **both**
latitude and longitude are present and valid; one without the other → no GPS
(not an error). A non-numeric or out-of-range latitude / longitude → `400`.

The endpoint builds a `Metadata` object `{ author, gpsLatitude, gpsLongitude }`
and calls `stripAndApply(bytes, meta)`. Note that `stripAndApply` with an
empty `Metadata` still strips, so a row with all three columns blank yields a
clean image, which is the desired behaviour.

**Response:**

- `200`, body = processed image bytes, `Content-Type` from `mimeFor(format)`,
  `Content-Disposition: inline; filename="image.<ext>"`,
  `X-Metaforge-Format: <jpeg|png|webp>`.
- `400` JSON `{ error }` — no file, bad lat/long, unreadable multipart.
- `401` JSON — missing/invalid key.
- `405` JSON — any method other than POST.
- `413` JSON — body over the limit (Vercel may return this itself; the handler
  must also cope gracefully if it receives the request).
- `415` JSON — TIFF or unrecognised format (message mirrors the UI's).
- `500` JSON — unexpected processing error; message included.
- `503` JSON — `METAFORGE_API_KEY` unset.

All JSON error bodies have the shape `{ "error": "<human readable>" }`.

**Build integration:** `npm run build` (`tsc -b && vite build`) must keep
succeeding and must type-check the new `api/` code (add a project reference
or include path so `api/` is covered by `tsc -b`). The Vite static output is
untouched. If a `vercel.json` is needed to set a function `maxDuration`, keep
it minimal; the default 10 s should be ample for a ~2 MB image.

**Tests:** add a Node test (`node --test` or the existing smoke-script style)
that invokes the handler with a real small PNG and JPEG and asserts: 401
without key, 400 on bad latitude, 200 with correct content-type, and that the
output contains the Artist tag and GPS coordinates when read back with
`piexifjs` (JPEG) / PNG chunk extraction (PNG). The existing `scripts/smoke.mjs`
shows how to read both back. Keep the test runnable with `npm test`.

**README:** add a short "API" section documenting the route, auth header, form
fields and an example `curl`.

### 2. n8n Worker changes

Workflow `QHneqwqMa6AlUA5P`. Current chain:

```
On Item From Parent → Generate Image → Download Image → Upload to Drive → Update Sheet
```

New chain:

```
On Item From Parent → Generate Image → Download Image → Stamp EXIF → Upload to Drive → Update Sheet
```

**New node "Stamp EXIF"** — `n8n-nodes-base.httpRequest` (v4.2):

- Method `POST`, URL `https://meta-forge-ten.vercel.app/api/process`.
- Authentication: Generic → **Header Auth** credential named
  `Metaforge API` (header `Authorization`, value `Bearer <key>`). The owner
  creates this credential in n8n with the same key set on Vercel. The key must
  not be pasted into node parameters.
- Body: `multipart/form-data` with
  - `file` → n8n binary file, input data field name `data` (the download
    node's output).
  - `author` → `={{ $('On Item From Parent').item.json.Author ?? '' }}`
  - `latitude` → `={{ $('On Item From Parent').item.json.Latitude ?? '' }}`
  - `longitude` → `={{ $('On Item From Parent').item.json.Longitude ?? '' }}`
- Response: format **File**, output binary property `data` (so the Drive node
  needs no change to which property it reads).
- Timeout 60 000 ms. `retryOnFail: true`, `maxTries: 2`, `waitBetweenTries`
  3000 ms, matching the neighbouring nodes' style.
- On error: default (stop and error), so a stamping failure fails the row and
  the sheet keeps `Processed = No`, which the dispatcher will retry on the next
  run. Do **not** set "continue on error".

**Rewire:** remove connection Download Image → Upload to Drive; add
Download Image → Stamp EXIF and Stamp EXIF → Upload to Drive.

**Unchanged nodes:** "Upload to Drive" still names the file from
`$('On Item From Parent').item.json['Image Name']` and reads binary `data`;
"Update Sheet" still matches on `row_number`. The Google Sheets "Get row(s)"
node in the dispatcher returns all columns, and the Worker's trigger
"On Item From Parent" is configured with `inputSource: "passthrough"`
(verified 2026-11-12 from the live workflow JSON), so the three new columns
reach the Worker with no change to the dispatcher's Execute Workflow mapping.

**What "stamped" means in practice:** the shared library writes `author` to
EXIF `Artist` **and** to an XMP packet as `dc:creator` (JPEG: XMP APP1; PNG:
`iTXt` chunk; WebP: XMP chunk), exactly as the Metaforge UI does today. GPS
goes to the EXIF GPS IFD only. So `exiftool` on an output file will show
`Artist`, `XMP-dc:Creator`, and the GPS tags, plus structural tags that are
not metadata (image size, PNG colour type, etc.). That is the acceptance
criterion; EXIF-only output is **not** required and the library must not be
forked to achieve it.

**Character set note (pre-existing library behaviour):** EXIF `Artist` is an
ASCII tag; characters above U+00FF (e.g. CJK) are mangled in the EXIF copy
while the XMP copy stays correct. Latin-script names, including accented
characters, are fine. Not in scope to fix; document it in the README API
section.

**Cutover order and activation:** the Worker is active but is only ever
invoked by the dispatcher, and the dispatcher is **inactive with a manual
trigger**, so nothing runs between steps unless someone clicks "Execute
workflow". No pause is needed. Still, do the steps in this order so a stray
manual run can never regenerate (and re-bill) rows because of a half-finished
cutover:

1. Code merged to `main`; Vercel deploys. Verify `curl -X POST
   https://meta-forge-ten.vercel.app/api/process` returns the `503`
   "API key not configured" JSON (proves the route built and is not shadowed
   by an SPA rewrite).
2. Owner sets `METAFORGE_API_KEY` on Vercel and redeploys. Verify an
   unauthenticated POST now returns `401`.
3. Owner creates the `Metaforge API` Header Auth credential in n8n and adds
   the three sheet columns.
4. Builder adds the "Stamp EXIF" node and rewires the Worker; validates with
   the n8n validation tool.
5. Owner (or builder, with the owner's go-ahead) sets one test row to
   `Processed = No` and runs the dispatcher once. Confirm with `exiftool` or
   the Drive preview that the uploaded PNG carries Artist, XMP creator and the
   GPS tags, and nothing from the original Fal.ai/OpenAI output.

If step 5 fails, the row stays at `Processed = No` and will be regenerated on
the next run, which costs one Fal.ai generation. Acceptable for a test row.

### 3. Deployment and secrets (owner steps, documented in README)

1. Generate a key (e.g. `openssl rand -hex 32`).
2. Vercel project → Settings → Environment Variables → `METAFORGE_API_KEY`
   for Production (and Preview if desired). Redeploy.
3. n8n → Credentials → new **Header Auth** → name `Metaforge API`, header name
   `Authorization`, value `Bearer <key>`.
4. Add `Author`, `Latitude`, `Longitude` columns to Sheet1.

**Repo state:** the owner confirms this working folder is the latest copy of
GitHub `main` (2026-11-12). Work in place: `git init`, add the remote
`git@github.com-work:admin-pracxcel/meta-forge.git` (the `github.com-work`
SSH alias is configured and authenticates), fetch `origin/main`, and
`git reset origin/main` so local history matches before committing. Confirm
`git status` shows no unexpected differences. There is no `vercel.json`, so
there is no SPA rewrite to worry about. Commit to `main` and push over SSH;
if the push is rejected, hand the branch to the owner.

## Decisions already made (by the owner unless marked "builder's call")

- Values come from sheet columns, per row, not fixed per run. (owner)
- Reuse Metaforge via an API rather than re-implementing in an n8n Code node.
  (owner, on builder's recommendation)
- Blank cell = omit field; GPS needs both coordinates; bad numeric input =
  400 and the row fails. (builder's call, stated to owner, not objected)
- Multipart/form-data over raw-body-plus-query-string, because n8n's HTTP
  Request node supports mixing text fields with a binary file natively and
  author text may be non-ASCII. (builder's call)
- Bearer token in `Authorization` header, env var `METAFORGE_API_KEY`.
  (builder's call)
- Fail closed when the env var is unset. (builder's call)
- Author is written to both EXIF Artist and XMP dc:creator, matching the UI;
  EXIF-only is not a requirement. (builder's call, see §2)
- Cutover sequencing as in §2; no pause of the Worker needed because the
  dispatcher is manual-only and inactive. (builder's call)
- Work in this folder, which the owner confirms is current `main`; attach git
  history by fetching the remote first. (owner)
